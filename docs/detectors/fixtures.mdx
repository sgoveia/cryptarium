# Fixtures & validation

Every new rule needs two small files: one that **must** match, one that **must not**.

**What you will do:** drop fixtures under `testdata/rules/<rule-id>/`, then run `make lint-rules`.

## Layout

```text
testdata/rules/<rule-id>/positive.<ext>
testdata/rules/<rule-id>/negative.<ext>
```

Use the full rule `id` as the folder name (example: `js.crypto.createcipheriv.aes`).

| Language | Extension |
|---|---|
| JavaScript | `.js` |
| TypeScript | `.ts` (still tests the javascript pack) |
| C | `.c` |
| Go | `.go` |
| Python | `.py` |
| Java | `.java` |

## What good fixtures look like

**Positive:** one real call site, nothing else.

```js
const crypto = require("crypto");
crypto.createCipheriv("aes-256-gcm", key, iv);
```

**Negative:** the same text only in a comment, or a lookalike that is not the crypto API.

```js
// crypto.createCipheriv is only mentioned in a comment.
```

Same idea for C: a real `RSA_generate_key_ex(...)` vs the name only in `/* ... */`.

## Commands

```bash
make lint-rules
make test
make check
```

Regenerate goldens only on purpose:

```bash
make golden
```

Review that diff. Do not accept it blindly.

<Warning>
  `make lint-rules` currently requires fixtures for the flagship Go RSA rule. Still add positive and negative fixtures for every rule you ship. That is what keeps false positives out of other people’s CI.
</Warning>
